# Landscape research: precision-first, non-LLM-judge code review reflexes

Context: SOR uses deterministic prep (git plumbing, AST splitting, reference
checks, fact tables) + a fast non-LLM classifier (Jev/TypeSafe) as judge, gated
at is_real >= 0.80, with a per-reflex adjudication ledger (ship >=0.70 sustained
over >=10 firings, retire <0.50). Goal: silence by default, findings only when solid.

---

## 1. Cheap/fast classifier as first-stage reviewer, LLM (or stronger model) as confirmer

- Google Tricorder (Sadowski et al., ICSE 2015) — https://research.google/pubs/tricorder-building-a-program-analysis-ecosystem/ (PDF mirror: https://www.cs.umd.edu/class/spring2019/cmsc414/papers/tricorder-building-a-program-analysis-ecosystem.pdf) — enforces a hard rule: any analyzer with a false-positive rate above ~10% (measured from developer dismiss/fix actions) gets pulled from production. **Stealable idea:** this is the closest real precedent to our 0.80 gate + ledger — but it's a *rate threshold on a deployed rule*, not a per-finding confidence score. Worth stealing: treat "below 10% FP tolerance" as the retirement bar for a whole reflex, independent of per-call confidence.
- BugLens / "Hitchhiker's Guide to Program Analysis Part II" (Li, Zhang, Pei, Qian) — https://arxiv.org/html/2504.11711v1 — classic deterministic-prepares/LLM-judges split: static analysis generates candidate reports, LLM is used purely as a validation filter on top, raising precision on a real Linux-kernel analyzer from 0.1 to 0.72. **Stealable idea:** nearly identical shape to SOR (prep → judge), direct precedent that the split works and quantifies the lift; worth reading closely for how they prompt/represent the candidate to the judge.
- AdaTaint — https://arxiv.org/html/2511.04023v1 — four-stage pipeline: static taint analyzer generates candidates → LLM extracts source/sink semantics + embeddings → a downstream *binary classifier* (not the LLM itself) does final filtering/ranking using LLM embeddings + static features (path length, sanitizer presence, reachability). Reports 84.3% precision, 75.4% recall, 43.7% FP reduction vs. baseline, 31% less triage time, developer trust 4.1/5 vs 2.7/5. **Stealable idea:** the "LLM produces features/embeddings, a cheap classifier makes the final call" inversion is interesting — opposite of SOR's "deterministic prep, fast classifier judges" but same principle of keeping the expensive reasoning out of the final gate. Also: they explicitly measure *trust*, not just precision — worth tracking qualitatively for SOR.
- BugStone — (fetched via arXiv, search didn't surface a clean arxiv ID but content confirmed) — rule-centric cascade: lightweight static matcher narrows candidates, single LLM pass validates against an extracted rule. 92.2% precision on their benchmark; at Linux-kernel scale, 22,568 flagged / 400 sampled / 246 confirmed (61.5% true-positive rate on the sample) — notably *not* using model confidence scores at all, relying on human sampling instead. **Stealable idea:** a caution, not an idea — their claimed precision (92.2%) on the curated benchmark doesn't match their own real-world sampled hit rate (61.5%), a reminder that benchmark precision overstates field precision; SOR's adjudication ledger (tracking real outcomes, not benchmark numbers) is the right response to this gap.
- Cost-ordered/calibrated cascades, general LLM-ops pattern — https://select.keenable.ai/r/cheap-text-classification-at-scale/Ty-uArS8QK7bcCt8fymhdQ and https://www.generalcompute.com/blog/cascade-inference-using-small-models-to-route-to-big-ones — standard pattern: small/cheap model tries first, a confidence/quality check decides whether to escalate to a bigger model; claims of retaining 97-99% of top-model accuracy at a fraction of cost. **Stealable idea:** nothing new for SOR's architecture itself (we deliberately don't escalate to an LLM at all), but confirms the "quality-gate-then-escalate" pattern is industry-standard — useful if SOR ever adds an optional LLM-confirm tier for findings near the 0.70-0.80 boundary instead of just silencing them.
- CodeRabbit (per comparison blogs, not a primary source) — https://levelop.dev/blog/best-ai-code-review-tools-2026-coderabbit-greptile-qodo-compared and https://aicodereview.cc/blog/coderabbit-vs-greptile — "40+ linter/SAST scanner layer running beneath the LLM... to catch more bugs while we filter out the noise." Greptile reported to produce far more false positives (~11) than CodeRabbit (~2) in one comparison; CodeRabbit explicitly does *not* expose confidence scores to users. **Stealable idea:** low confidence in these sources (vendor-comparison blogs, not primaries) — treat as directional only. The one real signal: hiding findings vs. showing confidence scores is a live UX choice among competitors; SOR's "silence otherwise" default matches CodeRabbit's choice, not Greptile's.

## 2. Classic false-positive suppression literature for static analysis

- Tricorder FP-rate gate (above) — same source, most load-bearing precedent.
- Survey of postprocessing approaches for static analysis alarms (130 primary studies), TU Eindhoven — https://research.tue.nl/en/publications/survey-of-approaches-for-postprocessing-of-static-analysis-alarms/ (full text: https://aserebre.win.tue.nl/SCAM2016.pdf) — taxonomizes techniques into clustering, ranking, pruning, automated FP elimination, static+dynamic combination, and simplifying manual inspection. **Stealable idea:** use this taxonomy as a checklist against SOR's reflex catalog — e.g. "ranking" and "pruning" map directly to our is_real score; "clustering" (dedup near-identical findings across a diff) is something SOR doesn't obviously do yet.
- Learning to Reduce False Positives in Analytic Bug Detectors — https://arxiv.org/pdf/2203.09907 (full read failed — PDF binary, only abstract-level info surfaced via search: trains a ranking classifier on static analyzer reports; related work cites decision-tree/AdaBoost classifiers hitting ~0.8 accuracy and RF/XGBoost up to 91% on true/false-positive prediction). **Stealable idea:** corroborates that a lightweight learned classifier on top of analyzer output is a well-trodden, successful pattern — not a new technique for SOR, but evidence the general approach (not LLM-specific) has precedent independent of LLMs.
- DeFP (via search snippet, no primary fetched) — two BiLSTM models ranking warnings by learned context patterns of historically labeled warnings. **Stealable idea:** "learn from the history of *this* warning type's past labels" is exactly the ledger idea SOR already adopted — nothing new, but another independent confirmation that per-rule historical accuracy is the standard signal, not whole-codebase features.
- Coverity usage empirical study (Imtiaz, Murphy, Williams, ISSRE 2019) — https://www.microsoft.com/en-us/research/?p=690690 — only 27.4%-49.5% (median 36.7%) of alerts across 5 long-lived OSS projects were ever acted on; median fix time was 96 days despite fixes being small (median 4 LOC). **Stealable idea:** a sobering real-world baseline for what "actionable" means at scale — most static-analysis alerts are simply never acted on regardless of truth value. For SOR's ledger, "developer never responded" needs its own bucket distinct from "dismissed as wrong," since silence conflates truth-value signal with priority/apathy signal.
- Semgrep Assistant / Multimodal autotriage — https://semgrep.dev/blog/2025/announcing-ai-noise-filtering-and-triage-memories and https://docs.semgrep.dev/semgrep-assistant/overview — LLM-based auto-triage layered on deterministic SAST; explicitly does **not** auto-close findings, only hides them with an explanation while keeping them visible to security teams; learns org-specific "memories" from past triage decisions. Claims 95-96% agreement with human triage across 250k+ findings/45+ enterprises, ~20% noise reduction (2.8x after 5 memories added by one beta user). Confidence-level slider exists for a separate "suggested fix" feature, but the FP-filtering decision itself isn't described as threshold-gated — it's agreement-rate validated post hoc. **Stealable idea:** the "memories" mechanism (org/rule-specific accumulated context that adjusts future triage) is a more sophisticated cousin of SOR's adjudication ledger — worth studying for how they let memories *downgrade* confidence without a human re-litigating every instance. Also strong validation of "hide-but-keep-visible-to-owners" as the safe failure mode, which maps to SOR's "silent telemetry" design.

## 3. Deterministic-prep-then-LLM-judge architectures (and the reverse)

- BugLens, AdaTaint, BugStone (all above, §1) are the primary examples found; all three are "deterministic/static generates candidates, LLM/learned-model judges or ranks" — the same shape as SOR, just with an LLM instead of a fast classifier as the judge.
- LLM-Enhanced Android Taint Analysis — https://arxiv.org/pdf/2608.24269 (title/abstract only, not fetched in full) — hybrid taint analysis + LLM reasoning; found via search, not independently verified beyond title. **Stealable idea:** flagged for completeness; not verified enough to extract a concrete technique — if this matters, worth a follow-up fetch.
- LATTE (binary taint analysis + LLM) — found via search snippet only (https://arxiv.org/pdf/2310.08275 is the related "Harnessing the Power of LLM to Support Binary Taint Analysis" paper) — claims 37 new real-world firmware bugs found, 7 assigned CVEs. **Stealable idea:** not independently verified in depth; cite with caution, but another data point that symbolic/deterministic analysis + LLM judgment finds real bugs beyond benchmarks, which is the standard SOR should eventually hold itself to (production CVEs/incidents, not just benchmark precision).
- No reverse case found (LLM generates candidates, deterministic code confirms) in this search pass — worth a dedicated follow-up search if useful, since SOR's prep step already resembles this in spirit (deterministic reference/fact checks constrain what the classifier is even allowed to see).

## 4. Selective prediction / abstention / conformal prediction for code review

- Fine-grained Confidence Calibration of LLMs in Automated Code Revision — https://arxiv.org/pdf/2604.06723 — abstention policy: suppress code revisions whose confidence falls below a pre-selected threshold; explicitly distinguishes *calibration* (does confidence match empirical correctness) from *abstention* (can the threshold support a deployment decision) as separate properties. **Stealable idea:** directly validates SOR's 0.80 gate design logic — but flags that SOR should separately verify calibration (is 0.80 *meaningfully* 80% correct) vs. just abstention behavior (does raising the threshold reduce FPs) since the paper treats these as two different things to measure.
- Uncertainty-Aware Abstention with Provable Alignment Guarantees — https://www.alphaxiv.org/abs/2607.04430 — general selective-prediction framework for LLMs: heuristic uncertainty scores alone don't carry statistical error-rate guarantees; need a calibration/conformal wrapper to get real guarantees. **Stealable idea:** a formal warning that resonates with SOR's empirical approach — the ledger (observed precision over >=10 firings) is effectively SOR's substitute for a conformal guarantee; this paper is the theoretical backing for why that empirical substitute is necessary (raw classifier scores aren't trustworthy error-rate estimates on their own).
- Does Confidence Calibration Improve Conformal Prediction? — https://arxiv.org/abs/2402.04344 — counterintuitive finding: naive calibration (e.g., temperature scaling) can *hurt* conformal prediction set efficiency; propose ConfTS to fix the mismatch. **Stealable idea:** a caution for any future tuning of Jev's confidence output — if SOR ever recalibrates the classifier's score distribution, re-validate against the ledger rather than assuming calibration monotonically helps gating.
- No deployed/production conformal-prediction-for-code-review system was found — this remains theoretical/academic as of this search. **Stealable idea / gap:** SOR's ledger-based empirical threshold-tuning (ship >=0.70 sustained, retire <0.50) is, as far as this search found, more operationally mature than anything published specifically for code review — worth noting as a possible point of genuine novelty rather than something to copy.

## 5. Feedback-ledger designs (per-rule precision tracking, auto-retire/auto-tune)

- Tricorder's FP-rate-gated production rule (§1/§2) is the cleanest real precedent for "auto-retire noisy rules," though it's binary (in/out at 10%) rather than SOR's three-tier ship/hold/retire bands.
- "Tracking developer behavior with respect to software analysis tools" (patent, cited generically, not Meta-confirmed) — https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11663341 and https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9727736 — describes tuning an analyzer's active rule set reactively based on observed developer dismiss/fix behavior. **Stealable idea:** same idea as Tricorder, filed as IP by a major vendor — reinforces that "disable/deprioritize rules developers consistently ignore" is considered valuable enough to patent, not just an academic nicety.
- Amazon "long term static analysis rule quality monitoring using true negatives" — https://assets.amazon.science/ed/11/a321529f4b61a1a35b9f4a7b8626/long-term-static-analysis-rule-quality-monitoring-using-true-negatives.pdf — **could not fetch (404 on direct link); title alone strongly suggests Amazon tracks rule quality over time using true-negative counts, not just true/false positives.** Flagging as unverified — recommend a follow-up search/fetch via Amazon Science's site search rather than the raw asset URL, since this title is the single most on-the-nose match for SOR's ledger concept found in this whole search.
- Semgrep Assistant "memories" (§2) — closest working *product* example of a feedback ledger: org-specific accumulated triage context that shifts future noise-filtering decisions, validated at 95-96% agreement with humans. **Stealable idea:** consider whether SOR's ledger should accumulate structured "memories" (e.g., "this repo always treats X pattern as intentional") rather than only a scalar precision-by-firing-count, to capture per-repo context Semgrep found valuable enough to productize.
- No example found of a system that *automatically* retires a rule purely from a numeric precision band the way SOR's >=0.70-ship/<0.50-retire policy does — most production examples (Tricorder, Semgrep) describe human-reviewed or binary on/off decisions rather than SOR's three-band sustained-count policy. **Stealable idea / gap:** this specific mechanic appears to be where SOR is ahead of documented industry practice; worth treating as a genuine design asset rather than assuming someone else already solved it better.

## 6. Genuinely novel 2024-2026 non-LLM or cheap-model code review approaches

- Feature Slice Matching (arXiv) — https://arxiv.org/html/2512.24858v1 — fully deterministic pipeline: slices known-bug code into "feature slices," embeds them (UniXcoder), ranks candidate matches elsewhere in the codebase by cosine similarity, *no LLM judge stage at all* — the authors explicitly tested LLMs as judges and found them "unstable for hard cases." Reports 56.4% of seed functions led to a new confirmed bug on Linux kernel v6.4-rc2, 77.6% recall@10 on a 76-pair benchmark, beats 9 prior tools (best baseline 61.3%). No explicit confidence threshold — gates purely by rank cutoff (top-10) and leaves final call to 2-minute human audits. **Stealable idea:** the strongest "genuinely non-LLM, works well" data point found. For SOR, the "embed a known-bad pattern, rank similar sites, human/classifier confirms top-K" structure is a plausible *additional* reflex type — a "we've seen this exact shape of bug before in this diff's neighborhood" detector — distinct from SOR's current fact-table-driven reflexes.
- Semgrep Assistant (§2/§5) is the most mature production deployment of AI-assisted (not necessarily LLM-as-final-judge) triage found in this window, and is 2025-dated — genuinely current, not legacy static-analysis literature.
- No small, purpose-built (non-LLM, non-generic-classifier) model specifically fine-tuned for *code review judgment* (as opposed to code-comment-quality or commit-intent classifiers, which do exist, e.g. https://huggingface.co/aieng-lab/gpt2_commit-intent) was found. The 2026 trend per vendor-comparison blogs (low-confidence sources, e.g. https://callsphere.ai/blog/llm-comparison-code-review-automation-small-models-may-2026) leans toward frontier LLMs with prompt engineering over small fine-tuned classifiers for this task. **Stealable idea / gap:** SOR's "fast classifier as judge" bet (Jev/TypeSafe, not a generic LLM) appears to be swimming against the current industry trend line, which is consolidating toward "more LLM, better prompts" rather than "smaller purpose-built judge." That's not evidence SOR is wrong, but it does mean there's little peer literature to lean on for calibration/validation methodology — SOR's own ledger is likely carrying weight other teams get from community-shared benchmarks.

## TOP 5 IDEAS TO GLEAN

1. **Google Tricorder's hard false-positive-rate gate for keeping a rule in production** — https://research.google/pubs/tricorder-building-a-program-analysis-ecosystem/ — Fit: direct precedent for SOR's retire-below-0.50 policy; suggests also tracking a rolling *rate* (not just a sustained-count band) per reflex, since Google's threshold is explicitly about dismissal rate from real usage, not a classifier's self-reported score.
2. **Feature Slice Matching's fully-deterministic, no-LLM-judge, rank-cutoff design** — https://arxiv.org/html/2512.24858v1 — Fit: closest thing to a sibling architecture for SOR (prepared evidence, no LLM, confidence via rank not probability) and the one place authors explicitly rejected LLM judgment as unstable — strong external validation for SOR's non-LLM-judge bet, plus a concrete new reflex idea (embed-and-match against a library of known bug shapes).
3. **Semgrep Assistant's "memories" + hide-but-keep-visible failure mode** — https://semgrep.dev/blog/2025/announcing-ai-noise-filtering-and-triage-memories — Fit: the most mature production analogue of SOR's "silent telemetry" default; its accumulated-context memories are a plausible upgrade path for SOR's ledger beyond a single scalar precision number.
4. **BugLens's precision-lift framing (0.1 -> 0.72) as a bar to cite/beat** — https://arxiv.org/html/2504.11711v1 — Fit: gives SOR a concrete, citable external number for "how much does a judge stage improve a noisy deterministic analyzer" — useful context for interpreting SOR's own 48-false-positives-in-a-week starting point and tracking improvement the same way.
5. **The abstention-vs-calibration distinction from confidence-calibration-for-code-revision work** — https://arxiv.org/pdf/2604.06723 and the conformal-guarantee warning at https://www.alphaxiv.org/abs/2607.04430 — Fit: a methodological check SOR hasn't necessarily done yet — verify that Jev's is_real score is *calibrated* (0.80 output really means ~80% correct) separately from verifying that the *gate* reduces false positives, since the two can diverge and the ledger alone conflates them.
